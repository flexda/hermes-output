Loop Engineer 가이드 (2026)

당신은 루프를 만드는 사람이 됩니다. 프롬프트를 치는 게 아니라, 에이전트를 계속 자극하고 결과를 검토하는 루프를 설계하세요.

루프 엔지니어링이란

프롬프트를 직접 치는 대신, 에이전트를 일정에 따라 자동으로 자극하고 결과(테스트, PR)를 검토해서 “완료 여부”를 판단하는 시스템을 만드는 것입니다. 진행 상황은 대화가 아니라 디스크, git, Linear, Slack에 남습니다.

왜 필요한가: 봇 운영, GitHub/Linear 연동, cron 기반 자동화를 이미 쓰는 당신에게는 자연스러운 다음 단계입니다.

루프 엔지니어의 3계층

  • Layer 1 — Context Engineering (2024): 컨텍스트 창에 넣을 정보를 조합합니다. 한 번 실행합니다.
  • Layer 2 — Harness Engineering (2025): 재시도, 도구 연결, 에러 핸들링 같은 한 번의 실행 래퍼입니다.
  • Layer 3 — Loop Engineering (2026): 스케줄로 반복 실행하고, 결과를 검증하고, 필요하면 다시 프롬프트를 보냅니다.

루프 6가지 핵심 블록

  1. Scheduling: 루프의 심장박동. cron, /loop, /schedule 등을 사용합니다.
  2. Worktrees: 병렬 실행을 위한 격리된 git 환경.
  3. SKILL.md: 프로젝트 규칙, 빌드 명령 등 반복 재사용되는 지식.
  4. MCP 커넥터: PR 열기, 이슈 읽기, Slack 알림 등 외부 도구 연동.
  5. Sub-agents (Maker/Checker): 작성과 검증을 분리하면 자기 검증 함정을 피합니다.
  6. STATE.md: 진행 상황, 실패 이력, 인간의 판단 필요 여부를 디스크에 기록.

적용 파일

아래 파일을 프로젝트에 넣어 루프의 안정성을 높이세요.

  • CLAUDE.md: 프로젝트 규칙 아카이브 (200줄 이내)
  • AGENTS.md: 매 실행 후 팩트/교훈을 업데이트
  • VISION.md: 목표 방향을 고정시키는 북극성 문서
  • PROMPT.md: 루프 시작 시 고정 컨텍스트(컨텍스트 드리프트 방지)
  • STATE.md: 현재 작업, 완료, 인간 확인 필요 상태를 추적
  • SKILL.md: 재사용 가능한 워크플로 하나당 하나씩

검증 원칙: NO 원칙

루프에는 반드시 거부 조건이 하나 있어야 합니다.

  • 테스트 실패 → NO
  • 타입 에러/컴파일 실패 → NO
  • 명세 불일치 → NO
  • 인간 검증 게이트 → NO
한계: 토큰 비용 가속 상승, “완료”의 오해, 코드 이해 부채, 인지 항복(cognitive surrender) 위험
