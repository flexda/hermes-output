Using Claude Code: The Unreasonable Effectiveness of HTML

Thariq Shihipar의 글을 기반으로, 왜 HTML이 Claude Code의 출력 포맷으로 유용한지, 언제 Markdown보다 낫고 언제는 여전히 Markdown이 더 나은지까지 바로 적용할 수 있게 정리했습니다.

한 줄 요약

이 글의 핵심은 “HTML이 Markdown보다 예쁘다”가 아닙니다. 사람이 실제로 읽고, 검토하고, 다시 작업에 쓰기 쉬운 출력물은 HTML이 더 잘 만든다는 점입니다.

특히 Claude Code처럼 긴 맥락을 다루는 에이전트에서는, 계획·리뷰·프로토타입·리서치 결과를 한 장의 HTML artifact로 만드는 것이 훨씬 실용적입니다.

information-dense reviewable artifact two-way interaction shareable link keep humans in the loop
핵심 문장

“The unreasonable effectiveness of HTML is not that it is a better markup language than Markdown. It is that HTML gives Claude Code a richer collaboration surface.”

HTML은 포맷 전쟁의 승자가 아니라, 협업 표면을 넓혀주는 도구로 이해하는 편이 정확합니다.

1) Markdown 대신 HTML을 고르는 이유

문제

Markdown은 짧은 메모에는 좋지만, 길어질수록 읽는 사람이 스크롤만 하다 끝내기 쉽습니다. 100줄이 넘는 계획서, PR 설명, 리서치 노트는 점점 “텍스트 덩어리”가 됩니다.

HTML의 장점

HTML은 제목, 강조, 표, 다이어그램, 탭, 버튼, 링크를 조합해 읽기 쉬운 구조를 만들 수 있습니다. 같은 내용이라도 HTML은 훨씬 더 “검토 가능한 형태”가 됩니다.

공유성

Markdown은 브라우저에서 즉시 예쁘게 보이지 않지만, HTML은 링크 하나로 바로 열립니다. 동료에게 “이거 한번 봐”라고 보낼 때 공유 비용이 낮습니다.

상호작용

HTML은 슬라이더, 버튼, 예시 토글, copy 버튼 같은 가벼운 인터랙션을 넣을 수 있습니다. 설명문이 아니라 작업용 인터페이스가 될 수 있습니다.

실무 해석: HTML을 쓰는 이유는 “예쁘니까”가 아니라, 사람이 실제로 읽고 재사용할 가능성을 높이기 위해서입니다.

2) 정보 밀도와 가독성

항목 Markdown HTML
긴 문서 길어질수록 평평해지고 읽기 피곤해짐 섹션과 시각 계층을 더 잘 분리할 수 있음
설명력 텍스트 중심이라 요점이 묻히기 쉬움 표, 박스, 색상, 다이어그램으로 관계를 보여줄 수 있음
편집 후 재사용 간단한 메모에는 편하지만 시각 자료는 약함 사람이 읽는 결과물로 재사용하기 쉬움
모바일 읽기 줄이 길어질수록 스크롤 비용이 커짐 레이아웃을 조절해 시선 이동을 줄일 수 있음

글에서 반복되는 메시지는 단순합니다. 사람이 실제로 읽게 만드는가? Markdown은 빠르게 쓰기 좋지만, HTML은 오래 읽히는 형태를 만들기 좋습니다.

3) 실제로 잘 맞는 작업들

Specs / planning

계획, 요건, 구현 방향을 한 번에 보여줘야 할 때 좋습니다. 여러 방향을 나란히 놓고 비교하거나, 일정·리스크·결정 사항을 분리해 보여줄 수 있습니다.

Code review

diff, severity, 영향 범위, 데이터 흐름을 한 화면에 묶을 수 있습니다. 단순 요약보다 리뷰 패킷처럼 보여줘서 검토가 쉬워집니다.

Design / prototype

HTML은 throwaway UI, 작은 인터랙션, 레이아웃 실험에 잘 맞습니다. “문장으로 설명하기 어려운 것”을 직접 눌러볼 수 있게 해줍니다.

Reports / research

긴 리서치 결과를 그냥 나열하지 말고, 관계와 구조가 보이도록 만듭니다. 읽는 사람이 다음 행동을 바로 떠올릴 수 있어야 합니다.

Learning / explainers

개념 설명, 인과 구조, 단계별 예시를 섞을 때 HTML이 강합니다. SVG, 색상, 콜아웃, 앵커 링크가 이해를 돕습니다.

Reusable context

한 번 만든 artifact가 다음 세션에서도 살아남으면, 그것이 곧 작업 컨텍스트가 됩니다. “읽고 끝”이 아니라 “다음에도 다시 쓰는” 문서가 됩니다.

4) 인간을 루프 안에 두는 방식

읽는 사람 기준

글의 중요한 포인트는 모델이 아니라 사람이 읽을지입니다. HTML은 인간이 읽는 시각적 구조를 강화해 에이전트의 산출물을 더 믿을 수 있게 만듭니다.

검토 가능한 산출물

Claude Code는 파일 시스템, git history, MCP, 브라우저 맥락까지 읽을 수 있으므로 HTML artifact를 단순 결과물이 아니라 검토 대상으로 삼기 좋습니다.

핵심: 좋은 출력은 더 많은 토큰이 아니라, 인간이 더 적은 노력으로 이해할 수 있는 구조입니다.

5) 언제 HTML / 언제 Markdown

HTML이 더 나은 경우

  • 길고 구조가 복잡한 계획서
  • 리뷰와 설명이 함께 필요한 PR
  • 그래프, 표, 다이어그램이 중요한 설명
  • 사람이 실제로 읽어야 하는 최종 산출물
  • 인터랙션이 있으면 이해가 쉬워지는 경우

Markdown이 더 나은 경우

  • 짧은 메모나 대화형 답변
  • 사람이 직접 빠르게 수정할 텍스트
  • 에이전트 내부 중간 산출물
  • 단순한 체크리스트나 임시 노트
  • HTML까지는 과한 문제

요약하면, 짧고 내부적인 건 Markdown, 길고 읽히는 건 HTML입니다. 글은 Markdown을 없애자는 게 아니라, 포맷을 작업에 맞게 고르자는 쪽입니다.

6) 바로 쓰는 프롬프트

아래 프롬프트는 글의 정신을 실제 작업으로 옮긴 버전입니다.

1) 계획을 HTML artifact로

Create a single self-contained HTML artifact for this task.
Make it readable in a browser, mobile-friendly, and easy to review.
Include:
- a high-level summary
- a module map or system map
- the proposed file changes
- risks by severity
- a staged plan
- open questions
- a copyable implementation prompt at the end

2) PR 리뷰를 HTML로

Help me review this PR by creating an HTML artifact that describes it.
I'm not very familiar with the streaming/backpressure logic, so focus on that.
Render the actual diff with inline annotations, color-code findings by severity,
and include a small diagram of the data flow.

3) 탐색용 HTML 브리프

Before choosing an implementation, brainstorm three directions:
1. the smallest safe change
2. the architecture-clean change
3. the fastest prototype
For each, explain what we learn, what we might regret,
and what the HTML artifact should show visually.

4) 설명문 대신 상호작용

I want to understand this better than a Markdown summary would allow.
Create an HTML page with:
- visual sections
- inline annotations
- a small interactive element or toggle where useful
- direct links to the source material
- a short takeaway at the top

7) companion gallery에서 보이는 패턴

공개 예시 갤러리와 요약들을 보면, HTML artifact는 단순히 “예쁜 문서”가 아니라 작업의 형태를 바꾸는 도구로 쓰입니다.

브레인스토밍

여러 방향을 나란히 놓고 비교하거나, 위험한 가정을 먼저 드러내는 형태. “팬아웃해서 옆에 놓고 보자”는 패턴이 반복됩니다.

구현 전 확인

blindspot pass, 인터뷰, reference map처럼 구현 전에 모르는 것을 먼저 밝히는 파일이 있습니다.

구현 계획

변경 파일, 마이그레이션 순서, 리스크 테이블, 테스트 계획을 한 장으로 모아 검토하기 쉽게 만듭니다.

변경 검증

implementation notes, status report, quiz, triage board처럼 구현 후에도 HTML이 살아 있어야 한다는 점이 강조됩니다.

리뷰 패킷

diff + annotation + severity + diagrams를 섞어 “눈으로 바로 판단 가능한” 형식을 만듭니다.

학습/설명

SVG, 인터랙션, 노트 구조를 활용해 개념을 시각화합니다. 설명을 읽는 대신 탐색하게 만듭니다.

마지막 정리

이 글은 HTML이 Markdown을 완전히 대체한다고 말하지 않습니다. 대신, Claude Code가 더 큰 작업을 다루기 시작한 지금은 작업의 표면을 더 풍부하게 만드는 포맷이 필요하다고 말합니다.

그래서 실제로는 이런 판단이 중요합니다:
짧고 단순한 건 Markdown, 구조와 검토가 중요한 건 HTML.

한마디로, HTML은 예쁜 출력이 아니라 사람과 에이전트가 함께 일하는 협업 인터페이스입니다.
