A Field Guide to Fable: Finding Your Unknowns

Thariq Shihipar의 글과 공개 요약을 바탕으로, 모델이 강해질수록 더 중요해지는 unknown unknowns를 찾는 방식과 바로 적용할 수 있는 실전 프롬프트를 한 페이지에 정리했습니다.

한 줄 요약

이 글은 “프롬프트를 더 잘 쓰는 법”보다 더 깊게 들어갑니다. Fable처럼 강한 모델을 쓸수록 문제는 모델 능력 자체가 아니라, 내가 아직 못 본 제약과 질문을 얼마나 빨리 드러내느냐로 바뀐다는 이야기입니다.

“The map is not the territory.” 프롬프트와 skills와 context는 지도이고, 실제 코드베이스와 제약과 의도는 영토입니다.
capability overhang blindspot pass unknown unknowns implementation notes human shift more ambitious work

1) Unhobbling Claude

핵심

더 똑똑한 모델일수록, 지나치게 무거운 시스템 프롬프트와 오래된 제약이 오히려 발목을 잡습니다. 그래서 Fable 세대에서는 가르치기보다 풀어주는 것이 중요해집니다.

현장 영향

Claude Code 계열 워크플로우는 시스템 프롬프트를 크게 줄이고, 모델이 더 넓은 가능성을 탐색할 수 있게 하는 방향으로 바뀝니다. 요지는 “더 많은 예시”보다 “덜 묶인 모델”입니다.

실무 해석: 이전 모델용으로 만들어 둔 장황한 규칙이 있다면, 새 모델에서는 그 규칙이 도움이 아니라 제약일 수 있습니다.

2) Finding your unknowns

이 글의 중심입니다. 문제를 받으면 곧장 구현하지 말고, 먼저 무엇이 빠져 있는지 밝히는 질문을 던집니다.

네 가지 지식 범주

범주 뜻 실무 예시
Known Knowns 프롬프트에 이미 적힌 것 “React 18을 쓰고 있다”
Known Unknowns 모른다는 걸 아는 것 “이 API의 rate limit을 확인해야 한다”
Unknown Knowns 너무 당연해서 적지 않았지만 보면 바로 알아차리는 것 암묵적인 디자인 기준, 팀의 관행
Unknown Unknowns 아직 생각조차 못한 빈칸 레거시 제약, 롤아웃 리스크, 숨어 있는 정책
Blindspot pass

가장 먼저 할 일입니다. “내가 놓치고 있는 것들을 알려줘”라고 묻고, 구현 전에 리스크를 나눠 봅니다.

Brainstorm + interview

애매한 요구는 답을 요구하기보다 선택지를 넓히는 게 낫습니다. Claude에게 당신의 스펙을 인터뷰하게 하면 숨은 전제가 드러납니다.

References

이미지, 스크린샷, 코드, 기존 문서처럼 실제 참고물을 넘겨줘야 지도와 영토의 차이가 줄어듭니다.

Implementation plan

데이터 모델, 인터페이스, 사용자 영향 범위처럼 바뀌기 쉬운 지점을 먼저 계획하고, 기계적인 리팩터링은 뒤로 미룹니다.

핵심 문장: 좋은 agentic coding은 모델이 더 많이 아는 게 아니라, 무엇을 모르는지 빨리 드러내게 하는 것입니다.

구현 중과 구현 후

  • 구현 중: 예상 밖의 결정은 implementation-notes.md에 기록
  • 구현 중: 어색한 edge case는 보수적으로 처리하고 이유를 남김
  • 구현 후: 요약문, 설명문, 퀴즈로 이해가 맞는지 검증
  • 구현 후: “내가 뭐를 놓쳤지?”를 다시 물어 다음 작업의 입력으로 삼음

3) Dealing with the grief

공개 요약들에 따르면, 이 파트는 손으로 코딩하던 감각에서 AI-assisted 개발로 넘어갈 때의 감정적 전환을 다룹니다. 단순히 생산성이 올라가는 문제가 아니라, 내가 하던 역할을 다시 정의해야 하는 순간이라는 뜻입니다.

왜 중요한가

모델이 일의 일부를 대신하면, 개발자는 “만드는 사람”에서 “무엇을 만들지 정하고 검증하는 사람”으로 무게중심이 이동합니다.

실전 태도

변화에 저항하기보다, 무엇이 빨라졌고 무엇이 중요해졌는지 적어보세요. 감정의 마찰을 메타데이터처럼 기록하면 다음 세션에서 덜 흔들립니다.

4) Being unreasonable

마지막 파트는 더 크게 요구하라는 메시지입니다. Fable 같은 모델을 쓰는 이유는 “적당히”가 아니라 기존에 포기했던 스케일을 다시 시도하기 위해서입니다.

무엇을 바꾸나

속도, 품질, 비용 중 하나를 포기하는 습관 대신, 실제로는 셋을 동시에 노릴 수 있는지 다시 질문합니다.

실무 예시

“이 정도면 괜찮다”가 아니라 “이걸 더 크게, 더 깔끔하게, 더 빨리 할 방법이 있나?”를 묻는 쪽으로 목표를 올립니다.

바로 쓰는 프롬프트

아래는 글의 흐름을 실제 작업에 옮긴 형태입니다.

1) Blindspot pass

나는 지금 [작업명]을 하려는데 이 코드베이스/도메인에 익숙하지 않아.
내가 놓치기 쉬운 unknown unknowns를 먼저 찾아줘.

특히 아래를 나눠서 봐줘:
- codebase risk
- product risk
- test risk
- rollout risk

아직 파일을 수정하지 말고,
1) 위험한 가정
2) 추가로 확인할 질문
3) 다음에 읽을 파일
4) 바로 실행 가능한 안전한 다음 행동
순서로 정리해줘.

2) Claude가 나를 인터뷰하게 하기

내 스펙과 요구사항을 한 번에 확정하지 말고,
질문을 하나씩 해줘.

우선순위는 이렇게 해줘:
- 답이 달라지면 설계가 바뀌는 질문
- 지금 안 정하면 되돌리기 어려운 질문
- 구현 전에 반드시 알아야 하는 질문

질문을 다 던지기보다, 가장 중요한 것부터 순서대로.

3) Implementation notes

작업 중 의도에서 벗어난 점, 바뀐 결정, 보수적으로 선택한 부분을
implementation-notes.md에 계속 추가해줘.

형식:
- decision: ...
- why: ...
- deviation: ...
- next_check: ...

4) 검증용 요약/퀴즈

지금까지의 변경 내용을 정리한 뒤,
내가 제대로 이해했는지 확인하는 짧은 퀴즈를 내줘.

퀴즈는 다음을 포함해야 해:
- 변경의 목적
- 가장 위험한 가정
- 아직 확인되지 않은 unknowns
- 내가 다음 세션에서 먼저 볼 파일

이 페이지를 실제 작업에 적용하는 예

예를 들어 새 auth provider를 추가한다고 해봅시다. 겉보기엔 버튼 하나 추가처럼 보여도, 실제로는 세션 갱신, callback URL, 환경변수, 테스트 더미, 배포 설정이 같이 움직일 수 있습니다.

나쁜 방식

“OAuth 버튼 추가해줘.”라고만 하고 바로 코드를 쓰면, 리다이렉트 URI 누락이나 테스트 환경 불일치 같은 빈칸이 남습니다.

좋은 방식

먼저 blindspot pass를 하고, 필요한 파일과 제약을 확인한 뒤, 구현 계획과 notes, 마지막 검증까지 한 번에 묶습니다.

적용 체크리스트

Done when 1 작업 시작 전에 내가 모르는 것 3개를 먼저 적는다.
Done when 2 blindspot pass를 먼저 돌리고 나서 구현한다.
Done when 3 데이터 모델·인터페이스·사용자 영향 범위를 분리해 적는다.
Done when 4 구현 중 바뀐 결정은 notes에 남긴다.
Done when 5 마지막엔 요약/퀴즈로 이해를 검증한다.
Done when 6 다음 세션에서 더 좋은 질문을 만들 수 있으면 성공이다.
