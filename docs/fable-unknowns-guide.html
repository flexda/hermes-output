A Field Guide to Fable: Finding Your Unknowns

Thariq의 글 핵심을 바탕으로, unknown unknowns를 찾고 더 나은 프롬프트·계획·검증 흐름으로 바꾸는 실전 가이드입니다. 바로 써먹을 수 있도록 예시 프롬프트와 체크리스트까지 포함했습니다.

1) 왜 이 글이 중요한가

이 글의 핵심은 단순합니다. 모델이 똑똑해질수록 문제는 더 이상 “모델이 못해서”가 아니라 내가 무엇을 빠뜨렸는지에 가까워집니다. 그래서 프롬프트를 잘 쓰는 것만으로는 부족하고, 내가 아직 모르는 것을 먼저 드러내는 과정이 필요합니다.

“The map is not the territory.” 프롬프트, skills, context는 ‘지도’이고 실제 코드베이스·제약·의도는 ‘영토’입니다.
문제가 커지는 이유

강한 모델은 애매한 지시도 자신 있게 밀어붙입니다. 그래서 지도에 빈칸이 있으면 그 빈칸이 조용히, 빠르게, 크게 번집니다.

좋은 대응

“정답을 바로 쓰게 하기”보다 “무엇이 부족한지 먼저 찾게 하기”가 더 효과적입니다. 즉, unknown unknowns를 먼저 밝히는 루틴이 필요합니다.

2) Map vs Territory를 실무 언어로 바꾸면

구분 무엇인가 실무에서 예
Map 프롬프트, skills, CLAUDE.md, 대화 맥락, 읽어온 파일 “새 결제 플로우를 만들어줘”라는 요청문
Territory 실제 코드, 암묵적 규칙, 레거시 제약, 진짜 사용자 의도 실제로는 결제 공급자가 2개이고, 한 곳은 모킹이 어려움
문제 지도가 영토보다 낡거나 비어 있으면 모델은 그 빈칸까지 채워버림 “이렇게 하겠지”식의 가정이 PR 전체를 오염

3) 4가지 지식 범주

Known Knowns

이미 프롬프트에 적힌 것. 예: “React 18을 사용 중”

Known Unknowns

모른다는 걸 아는 것. 예: “이 API의 rate limit은 모르겠다”

Unknown Knowns

너무 당연해서 안 적지만, 보면 바로 알아차리는 것.

Unknown Unknowns

생각조차 못한 빈칸. 이 글이 가장 중요하게 보는 대상입니다.

핵심: 실패를 막는 포인트는 known unknowns를 메모하는 것보다, unknown unknowns를 찾는 질문을 먼저 넣는 데 있습니다.

4) 실전 워크플로우

  1. Blindspot pass로 빈칸 찾기
  2. Exploration / brainstorming으로 방향 확정
  3. Structured interview로 애매함 해소
  4. Implementation plan으로 바뀌기 쉬운 부분 정리
  5. implementation-notes.md에 결정과 예외를 기록
  6. 퀴즈/리뷰로 이해 여부를 검증
1. Blindspot pass

구현 전에 “내가 뭘 놓치고 있나?”를 묻습니다. 가장 빠른 비용 절감 단계입니다.

2. 계획 후 실행

바로 코딩하지 말고, 데이터 모델·인터페이스·사용자 영향 범위를 먼저 계획합니다.

3. 기록

구현 중 바뀐 점을 별도 노트로 남기면 다음 시도에서 같은 실수를 반복하지 않습니다.

4. 검증

마지막엔 설명문/퀴즈/HTML 리포트로 스스로 이해했는지 확인합니다. “만들기”보다 중요합니다.

5) 바로 쓰는 프롬프트 예시

아래 문장들은 글의 흐름을 실제 작업에 옮긴 버전입니다.

Blindspot pass

나는 지금 새 auth provider를 추가하려고 해. 이 코드베이스의 auth 모듈은 거의 모르고 있어.
내가 놓치기 쉬운 unknown unknowns를 먼저 찾아줘.
특히 아래를 중심으로 봐줘:
- 아키텍처에 영향을 주는 질문
- 데이터 모델 변경 가능성
- 보안/세션/리다이렉트/테스트의 누락 가능성
- 내가 다음으로 읽어야 할 파일

출력은:
1) 놓치기 쉬운 질문
2) 위험한 가정
3) 다음 행동 순서
4) 내가 너에게 더 잘 물어야 할 질문

Structured interview

질문을 한 번에 하나씩 해줘.
단, 아래 기준으로 우선순위를 정해줘:
- 답이 바뀌면 설계가 달라지는 질문
- 지금 안 정하면 나중에 되돌리기 어려운 질문
- 구현 전에 꼭 알아야 하는 질문

질문을 다 던지기보다, 가장 중요한 것부터 순서대로 물어봐.

Implementation notes

작업하면서 의도에서 벗어난 점, 바뀐 결정, 보수적으로 선택한 부분을
implementation-notes.md에 계속 추가해줘.

형식:
- decision: ...
- why: ...
- deviation: ...
- next_check: ...

6) 예시: auth provider 추가 작업

예를 들어 새 로그인 공급자를 추가한다고 해보겠습니다. 겉보기엔 “버튼 하나 더 붙이면 끝”처럼 보여도, 실제로는 세션 갱신, callback URL, 환경변수, 테스트 더미, 배포 설정이 함께 움직일 수 있습니다.

나쁜 접근

“OAuth 버튼 추가해줘.”만 남기고 바로 코드 작성. 결과: 리다이렉트 URI 누락, 테스트 환경 불일치, 보안 검토 빠짐.

좋은 접근

먼저 blindspot pass → 필요한 파일 확인 → 구현 계획 → 예외 기록 → 마지막 검증. 결과: 처음엔 느려 보여도 되돌림 비용이 크게 줄어듭니다.

작업 흐름 예시

  1. 현재 auth 폴더와 환경변수 목록 파악
  2. 리다이렉트와 세션 처리 경로 확인
  3. 필요한 변경 범위를 한 장의 계획으로 정리
  4. 구현 중 예상 밖 제약은 notes에 남김
  5. 최종적으로 “내가 무엇을 놓쳤는지”를 다시 질문

7) 오늘 바로 적용 체크리스트

Done when 1 새 작업 시작 전에 “내가 아직 모르는 것” 3개를 먼저 적는다.
Done when 2 구현 전에 blindspot pass를 한 번 돌린다.
Done when 3 계획에서 데이터 모델·인터페이스·사용자 영향 범위를 분리해서 쓴다.
Done when 4 작업 중 바뀐 판단을 implementation-notes.md에 기록한다.
Done when 5 마지막에 요약/퀴즈로 스스로 검증한다.
Done when 6 다음 세션에서 같은 작업을 다시 해도, 처음보다 더 좋은 프롬프트를 쓸 수 있다.
