1. 왜 이 글을 다시 짰나

핵심 범위

읽기 컨트롤

학습

2. Spec-Driven Development

why now

AI 시대의 병목은 구현이 아니다

에이전트는 코드를 빠르게 생성하지만, 그만큼 리뷰·통합·검증이 뒤따라야 합니다. 그래서 개발자의 역할은 단순 코더에서 기술 설계자에 가까워집니다.

원문은 이 변화를 vibe coding과 vibe-in-production의 차이로 설명합니다. 생산 단계에서는 제어 가능성과 재현성이 중요합니다.

source of truth

좋은 명세는 아키텍처의 북극성

좋은 스펙은 컨텍스트 단절을 막고, 인간과 AI가 같은 기준을 보게 만듭니다. 원문은 스펙을 specs/ 폴더에 두는 예를 듭니다.

명세가 견고하면 코드는 다시 생성할 수 있습니다. 즉, 코드보다 기준이 더 오래 갑니다.

what to include

좋은 명세의 구성

  • 전체 기술 설계
  • 데이터베이스 스키마와 API 계약
  • 다이어그램과 도구/라이브러리 버전
  • 왜 이걸 만드는지에 대한 배경 설명
format

형식 선택

  • Markdown은 읽기 쉬운 앵커 역할
  • YAML은 구조화된 설정에 유리
  • 핵심은 사람이 읽을 수 있으면서 에이전트도 잘 해석하는 것
bdd

Behavior-Driven

  • Scenario / Given / When / Then
  • State → Action → Outcome으로 생각하게 만듦
  • 사용자 관점의 행위로 요구사항을 구체화
학습자 메모

이 장의 핵심은 “명세를 잘 쓰면 코드는 버릴 수 있다”가 아니라, 명세를 먼저 설계해야 에이전트 작업이 안정적으로 반복 가능해진다는 점입니다.

3. 지침은 어디에 두나

위치 역할 언제 쓰나 주의점
Chat interface 짧은 오케스트레이션과 즉시 피드백 “지금 이 기능만 고치기” 같은 순간 작업 짧은 컨텍스트, 긴 문서에는 부적합
specs/ folder 버전 관리되는 설계, BDD, 계약, 스키마 프로젝트 기준 문서를 보관할 때 스펙이 소스 오브 트루스여야 함
System prompts / profiles 에이전트의 정체성과 기본 규칙 도구별·프로젝트별 환경 설정 전역 설정과 프로젝트 설정이 충돌하지 않게
MCP / tools 시스템과 외부 자원의 연결 데이터베이스, 파일, API 연동 권한과 정책을 분리해서 설계
use cases

용도별 프롬프트

  • 프로젝트 생성 — 폴더 구조, 스택, 테스트, 문서, 로그를 먼저 제안하게 한다
  • 기능 생성 — 기존 스타일, 네이밍, 오류 처리 방식을 따르게 한다
  • 버그 수정 — 증상보다 재현 명령과 실패 테스트를 먼저 확보한다
  • 문서 작성 — README/CHANGELOG와 도큐스트링을 기준으로 동기화한다
  • 데이터 작업 — SQL/명령어를 명시적으로 남기게 한다
결정 포인트

긴 설계 문서를 채팅에 붙여넣는 대신, 어떤 정보는 채팅에 두고 어떤 정보는 저장소에 둘지 구분해야 합니다. 이 분리가 컨텍스트 낭비를 줄입니다.

프롬프트 재작성 예시 보기

나쁜 프롬프트: “로그인 페이지 만들어줘.”

좋은 프롬프트: “기존 코드 스타일을 유지하고, 폴더 구조와 기술 스택을 먼저 제안한 뒤, 테스트·문서·로깅까지 포함해 로그인 기능을 추가해줘.”

4. 용도별 프롬프트를 어떻게 다르게 쓰나

Builder

기능 생성

기존 코드베이스 위에 새 기능을 얹을 때는 스타일 일치와 diff 확인이 중요합니다.

Forensic

버그 수정

증상 프롬프트 대신 로그, 재현 명령, 실패 테스트를 이용해 원인을 찾아야 합니다.

Author / Librarian

문서 / 데이터

문서는 source of truth, 데이터 작업은 실행된 SQL과 명령어가 남아야 합니다.

prompting principle

프롬프트는 제약을 먼저 적을수록 강해집니다.

use cases

프로젝트 생성, 기능 생성, 버그 수정은 서로 다른 프롬프트가 필요합니다.

5. MCP: 하나의 통합, 모든 프레임워크

concept

MCP는 연결 계층이다

하나의 MCP 서버를 만들면 데이터베이스, API, 파일 시스템 같은 자원에 여러 MCP 호환 에이전트가 같은 방식으로 접근할 수 있습니다.

원문은 MCP를 USB-C에 비유합니다. 핵심은 “한 번 연결해서 여러 도구에 재사용한다”는 점입니다.

architecture

서버와 클라이언트

서버는 도구를 노출하고, 클라이언트는 그 도구를 발견해 호출합니다. 이 구조가 분리되어 있어야 연동과 교체가 쉬워집니다.

백서는 SQLite를 노출하는 간단한 서버와 stdio로 연결하는 클라이언트 예시를 제공합니다.

copyable snippet

MCP 서버 스켈레톤

import sqlite3
from mcp.server import Server
from mcp.server.stdio import stdio_server

server = Server("knowledge-base")
db = sqlite3.connect("knowledge.db")

@server.list_tools()
async def list_tools():
    return ["query_knowledge"]

@server.call_tool()
async def call_tool(name, arguments):
    if name == "query_knowledge":
        sql = arguments["sql"]
        if not sql.strip().upper().startswith("SELECT"):
            return ["Only SELECT queries allowed"]
        return db.execute(sql).fetchall()
copyable snippet

MCP 클라이언트 스켈레톤

from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

server_params = StdioServerParameters(command="python", args=["mcp_server.py"])
async with stdio_client(server_params) as (read, write):
    async with ClientSession(read, write) as session:
        await session.initialize()

6. 팀 문화와 코드 리뷰

problem

세 가지 마찰

  • 대형 PR로 인한 병목
  • 같은 파일을 동시에 만지는 merge conflict
  • 오래된 스냅샷 때문에 생기는 context fragmentation
response

리뷰 기준 재설계

  • 스타일보다 아키텍처 보존에 집중
  • Conditional LGTM처럼 자동 테스트 통과를 전제로 승인
  • 실수의 책임을 사람보다 프로세스에 묶기
scale

리뷰 에이전트의 단계

  • Managed: 바로 쓰는 SaaS
  • Hybrid: CI에 붙인 맞춤형 리뷰
  • Custom: 장기 컨텍스트와 온콜을 가진 전용 런타임
지속 가능성은 왜 여기서 나오는가

AI 사용량이 늘면 승인 피로와 리뷰 피로도 같이 늘어납니다. 원문은 이 문제를 기술 문제가 아니라 조직 문제로 다루며, 디지털 quiet hours와 주간 insight session 같은 경계 설정을 제안합니다.

7. 제로 트러스트 개발: 안전망 구축

핵심 결론

에이전트는 목표를 향해 최적화하지만, 그 목표가 “해야 하는 일”인지 “할 수 있는 일”인지는 스스로 보장하지 못합니다. 그래서 가드레일이 필수입니다.

안전 전략의 순서

권한을 줄이고, 샌드박스로 가두고, 중요한 행동은 사람에게 넘기고, 테스트와 평가로 검증하고, 정책과 컨텍스트 위생으로 입력·출력을 정화합니다.

Guardrails

정책과 권한

Structural gating으로 역할/환경 기준을 먼저 막고, Semantic gating으로 의도까지 검사합니다.

Sandbox

격리 실행

에이전트 작업을 저권한 컨테이너나 샌드박스 터미널에서 돌려 blast radius를 줄입니다.

HITL

사람의 최종 책임

중요한 행동은 자동 승인하지 말고, 사람이 최종 sign-off를 하도록 설계합니다.

copyable snippet

정책 YAML 예시

environments:
  localhost:
    blocked_tools:
      - send_email
roles:
  viewer:
    allowed_tools:
      - list_files
      - read_file

컨텍스트 정화 스케치

def resolve_context(template_str, override_state=None):
    # Replace [[VARIABLE_NAME]] with safe runtime values
    # Prefer explicit overrides, then environment variables
    return sanitized_template
tests

AI 생성 테스트 커버리지

  • 먼저 실패하는 단위 테스트나 재현 명령을 만들게 한다
  • 실행 가능한 체크를 코드베이스에 남긴다
  • 자동 검증으로 회귀 재발을 막는다
evaluation

평가와 정책 서버

  • 테스트는 binary, 평가는 score-based
  • Policy server는 도구 호출 전에 차단/검사한다
  • PII masking, placeholder injection, output sanitization이 중요하다

8. 요약과 다음 행동

한 줄 해석

AI가 코드를 빠르게 만들어도, 검토·통합·안전은 자동으로 해결되지 않습니다.

next action

학습자가 바로 할 일

  1. 내 프로젝트의 source of truth 위치를 정한다

  4. 리뷰 기준을 스타일이 아니라 통합과 안전으로 바꾼다
